# AI usage disclosure

AI assistance was used during implementation, test development, SQL/architecture discussion, CI hardening, and documentation. In Phase 8 it assisted with the Dockerfile, Compose orchestration and database bootstrap, Development Swagger setup, related tests, and the English README and this disclosure. This is not a claim that any particular code or test was written independently by a human, nor an attribution to an unverified model identity.

The human owner directs scope, reviews the work, supplies/approves configuration and delivery decisions, and owns commits, pushes and the final submission tag. AI suggestions and generated changes require verification; assistance is not evidence of correctness by itself.

## A real mistake and its correction

An earlier AI-assisted CI vulnerability gate searched report text with `grep` rather than validating the JSON structure. It could falsely treat an empty `"vulnerabilities": []` array as a vulnerability, while accepting empty or malformed reports because the searched substring was absent. That meant both false alarms and unsafe successful exits.

The correction used structural `jq` parsing in [.github/scripts/check-vulnerabilities.sh](.github/scripts/check-vulnerabilities.sh), with explicit exit codes: 0 for a valid clean report, 1 for vulnerabilities, and 2 for missing, empty, malformed or structurally invalid input (or missing `jq`). It checks top-level and transitive packages rather than relying on textual presence.

A later adversarial check found another real hole: present collection fields with `false` or `null` were being accepted. The [regression script](.github/scripts/test-check-vulnerabilities.sh) reproduced this as **RED: 21 passed, 8 failed**. The fix distinguishes an absent optional collection from a present non-array value; after correction, **GREEN: 29/29 passed**, checking exact exit codes and stdout/stderr. This example illustrates why a plausible AI-generated parser still needed negative cases and review.
